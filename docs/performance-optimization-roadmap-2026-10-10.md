# KADR Studio — план системной оптимизации AI-монтажа

**Статус:** план, без изменений поведения программы. **Ветка разработки:** `codex/dramatic-montage`.  
**Базовая проверка:** 2026-10-10, `test-reports/runs/20261010_101825_6a4da318/`, исходный код `fd3872d5`.  
**Дата:** 2026-10-10.

## 1. Задача и ограничения

Цель — получить быстрый, качественный, объяснимый и воспроизводимый монтаж на локальных моделях. Нельзя просто пропускать проверки или скрывать ошибки для получения PASS.

**Приоритеты в порядке важности:** (1) смысловая цельность и важные переходные действия; (2) достоверные исходные кадры и таймкоды; (3) реальный успешный полный E2E с ASR, VLM, планом, FFmpeg и повторным запуском из кэша; (4) скорость; (5) стабильность и возможность диагностики.

Не подменять тест реальной модели фиктивным ответом; не уменьшать незаметно 180-секундный вход; не преобразовывать TIMEOUT в PASS; не обрезать ответ модели по искусственному лимиту без проверки качества; не отбрасывать короткие действия, клипы или речевые мосты только ради экономии времени. Изменение интервалов должно сохранять реальные source-PTS, семантическую принадлежность и доказательства.

## 3. Цели и бюджеты

### Приёмочный критерий

Для **180 секунд**: полный запуск `ТЕСТЫ/2_ПОЛНАЯ_ПРОВЕРКА_С_ИИ.bat` на той же серии, с действительными ASR/VLM, планом, рендерингом и повторным использованием кэша, завершается **PASS в пределах 1800 с**. Желательная цель после стабилизации — **≤20–25 мин** для этого теста с запасом, но не ценой снижения качества.

Ориентировочный бюджет для поиска узких мест, **не тайм-ауты с принудительным пропуском этапов**:

| Компонент | Бюджет на 180 с |
|---|---:|
| Python, React, технический FFmpeg E2E, подготовка реального фрагмента | 4:00 |
| ASR | 0:30 |
| Видеопланы и смысловые границы | 3:00 |
| Первичный визуальный анализ | 5:30 |
| Повторное смысловое сокращение | 6:00 |
| Титры, связность, финальные проверки | 3:00 |
| Планирование, реальный рендер, проверка MP4/кэша | 4:00 |
| Непредвиденные расходы, загрузка моделей, повторные попытки | 4:00 |
| **Всего** | **30:00** |

Это гипотезы, а не гарантии. При невозможности достигнуть бюджета проверяем запросы, качество и оборудование; не притворяемся, будто какой-то этап завершён.

Для исходников **23–30 минут** отдельно строим масштабирование по реальному количеству кадровых событий, ASR-слов, смысловых сцен и запросов, а не прямую формулу «3 минуты × 10». Первичная цель на длинном видео — отсутствие экспоненциального роста, обязательные чекпойнты, объяснимое время и успешность. Целевое абсолютное время для длинного видео назначаем после трёх сопоставимых замеров.

## 4. Исполнение: этапы и точки проверки

### Этап 0 — Эталон качества и воспроизводимый бенчмарк (без изменения монтажа)

1. Зафиксировать exact source excerpt `sha256`, FPS, PTS, длительность, входные настройки, модельные GGUF/projector хэши, конфигурацию ускорения CPU/GPU и ревизию кода, не публикуя частные пути или кадры.
2. Снимать baseline не только на всём видео, но и на нескольких намеренно трудных ситуациях: связывание/посадка в автомобиль; короткие физические действия; длинные вопрос–ответ; эмоциональный крик; перемещение между локациями; шутка/пауза; действие, которое объясняет следующую реплику; границы заставки и финала.
3. Для каждой ситуации фиксировать эталонные source-PTS, обязательные причинные фрагменты и запрещённые «прыжки»; оценивать фактическую потерю контекста и корректность речи. Не объявлять число сцен само по себе качественной метрикой.
4. Запустить два режима сравнения: короткие unit-тесты без ИИ и реальный полный 180-секундный тест с ИИ. Все изменения проверять на неизменном наборе.
5. Создать машинный diff-отчёт «было/стало»: версии моделей, число вызовов на стадию, запрошенные/обработанные токены, длительность, число scene/chunk, качество, MP4/ASR, PASS/FAIL.

**Критерий завершения:** одна кнопка генерирует сопоставимый отчёт, baseline сохранён, эталоны готовы.

### Этап 1 — Полная телеметрия без утечки пользовательских данных

1. Для **каждого** локального VLM вызова записывать разрешённые поля: `stage`, модель (внутренний псевдоним), `request_id`, размер изображения/число страниц, длина входа, prompt/eval tokens и скорости (если llama.cpp отдаёт), output tokens, reasoning output count, `start/finish`, latency prefill/decode, success/error, факт CPU fallback, cache hit/miss, retry.
2. Измерять холодную загрузку Qwen4B/9B и время перехода между моделями, возможную выгрузку/повторную загрузку; записывать свободную RAM/VRAM только по согласованным локальным счётчикам.
3. Помечать каждую story-проверку своим назначением: `credit_classifier`, `choose_units`, `omission_proof`, `visual_continuity`, `global`, `titles`, `closing`, `framing`. Чётко отделить интеллектуальные вызовы от загрузки модели и FFmpeg.
4. Записывать **отдельно** ожидание, выполнение и незавершённые интервалы при TIMEOUT; не выдавать незавершённую длительность за ноль.
5. Агрегировать в `test-reports/runs/<id>/stage_timings.json|md`, `ai_diagnostics.json`, новую таблицу latency p50/p90/p95, запросов/минуту, cache hits. Отправлять только allowlist чисел/служебных типов — никаких реплик, кадра, prompts/response или абсолютных путей.

**Критерий завершения:** точная причина 135–159-секундных запросов выявляется по времени prefill/think/decode/model startup; тайм-ауты оставляют полезный частичный отчёт.

### Этап 2 — Оптимизация самого дорогого этапа `story_refinement`

1. Промерить `Qwen3.5-9B thinking=True` отдельно: количество запросов `refine_story`, количество входных единиц, размер JSON schema, визуальные страницы, reasoning tokens, source-to-story latency. Найти первые два медленных вызова 135/159 с.
2. **Не отключать размышление сразу у всех.** Сравнить на эталонах 3 варианта: текущая 9B/think 512, та же 9B с ограниченным reasoning budget, и обычная 9B без thinking с выборочной обязательной независимой проверкой сомнительных исключений.
3. Реализовать маршрутизатор по риску решения: простое безопасное сохранение unit — дешёвый путь; сложное удаление, переходное действие, юмор, эмоциональная реакция, смена состояния, противоречие — полноценная reasoning-проверка. Уровень риска определяется явно текущими свидетельствами, не «уверенностью» модели как единственным доказательством.
4. Уменьшить повторную подачу одинаковых доказательств: краткий валидированный контекст и ссылки на unit/frame IDs для внутренних технических детей. **Независимый `verify_omissions` сохраняется** для любого реального исключения.
5. Проверить «20 смысловых родителей / ~68 технических детей»: где отдельное решение неизбежно, а где можно в одном обращении разобрать соседние дети с независимыми unit IDs и полным покрытием; запрещать смешивать владельцев разных смысловых сцен без строгой карты.
6. Уменьшить дублирующую проверку титров: один проверенный положительный/отрицательный result по идентичным кадрам и версии модели, а не повторный полный просмотр для каждого следующего этапа.
7. Для любого упрощения хранить `decision_id`, `evidence_hash`, `risk`, `model/version`, `confidence`, нужность независимой ревизии, outcome. Смена prompt/schema сбрасывает только затронутую часть кэша.

**Критерий завершения:** этап `story_refinement` выходит из TIMEOUT, вторая и третья long-tail latency сокращаются, пропуск сюжетного моста или неподтверждённое удаление отсутствуют на эталонах.

### Этап 3 — Визуальный анализ сцены и размер технических фрагментов

1. Пересмотреть `bounded_chunks` и `inference_samples` на реальных 68 технических фрагментах. Разделить «изображений на VLM» и «смысловых границ сцен».
2. Адаптивно регулировать количество кадров (в рамках безопасного `MAX_INFERENCE_FRAMES`) по действию/движению/смене состояния, сохранив все исходные PTS и аудиоконтекст. Больше кадров для связывания/машины/объясняющей физической перемены, меньше — для длинной статичной беседы.
3. Проверить `recovery_trigger`: сколько раз он вызывается, из-за какого confidence, какова фактическая польза от повторного просмотра. Избегать восстановления только из-за отсутствующих несущественных полей, но не отказываться от него при потере смысла/невалидном ответе.
4. Кэшировать проверенные storyboards и page hashes без повторной FFmpeg-экстракции, когда исходник, PTS и sampling policy идентичны.
5. Валидация: полное покрытие исходных кадров фрагментами, отсутствие frame-empty/неразделимых интервалов, не теряются действия длительностью 1–2 с, не появляются обрывы речи/микровырезы.

**Критерий:** уменьшена стоимость первичного анализа при неизменном/лучшем recall смысловых действий.

### Этап 4 — Проверки смысловых границ (второй крупный bottleneck)

1. Проанализировать все 340 кандидатов: слабые cuts, verified changes, безречевые крупные переходы, физические изменения; сколько из 74 VLM вызовов действительно подтвердили новую смысловую сцену.
2. Для обычных смен камеры попробовать дешёвую повторяемую проверку визуального embedding/ASR/рекуррентности, но **не вводить глобальный запрет сцен короче N секунд**.
3. Для важных «до/во время/после» сохранять три настоящих кадра и полную серию переходных действий. Определённые state_probe или dialogue_break обязаны иметь более высокий приоритет.
4. Экспериментировать с более эффективным schema и кратким вопросом модели, измерять response tokens и частоту uncertain. Допускать вариант совместной оценки нескольких **соседних** границ, только если соблюдены независимые исходные timestamps.
5. Возвращать uncertain, если доказательств недостаточно; не объявлять границу `accepted` ради красивой статистики.

**Критерий:** boundary stage приближается к ~3 мин на 180 с без ухудшения качества сценарных стыков и без увеличения «неизвестных» сцен.

### Этап 5 — Производительность модели и аппаратное профилирование

1. Автоматически фиксировать RAM/VRAM/GPU/CPU, квантование, offload layers, число потоков, время загрузки llama.cpp, использование CPU fallback. Никаких предположений о видеокарте только по прошлому оборудованию.
2. A/B маленькими воспроизводимыми тестами: `--no-cache-prompt`, `--cache-ram 0`, prompt-cache, `--image-min/max-tokens`, максимальный размер страницы, context 8192, schema constraints, `-np`, `--reasoning-budget`. Менять по одному параметру.
3. Не включать конкурентную работу 4B+9B автоматически: если RAM/VRAM недостаточно, будет медленнее и опаснее для стабильности. Провести отдельный тест memory pressure и GPU/CPU fallback.
4. Безопасный вариант: короткие тёплые сессии и кэширование общих prompt-prefix при доказанной совместимости; отсутствие регресса приватности и воспроизводимости.
5. Полная таблица: cold/warm startup, prefill t/s, decode t/s, 95-й перцентиль, память и качество JSON.

**Критерий:** реальное ускорение в токенах/сек и успешных ответах на тех же входах, а не случайный PASS на одном коротком фрагменте.

### Этап 6 — Исключить повторную семантическую работу в downstream

1. Составить граф зависимостей проверок: `scene_analysis` → `story_refinement` → `credit/title/source_roles` → `global_visual` → `selection_adjudication` → `pacing` → `framing`. Для каждого написать, какое решение новое, какое дублируется и какое независимо обязательно.
2. Ввести проверяемый реестр решений/proofs с ключом `source_hash + PTS + frame_hash + semantic_prompt_version + model_identity`. Использовать уже доказанное только при полном совпадении полномочий и условий.
3. Сохранить независимую проверку **удалений** из сюжета, новых физических состояний, титров, превью и важного контекста; убрать только бессмысленный повтор одинаковой модели на тех же кадрах.
4. Строгая инвалидация изменений source/ASR/shot/frame/model/policy, атомарная запись, обрыв в любой точке, повтор без нового анализа уже завершённых валидных единиц.

**Критерий:** при возобновлении теста новый запрос нужен только для отсутствующего либо действительно изменившегося свидетельства; идентичный повтор даёт тот же итоговый plan/output hashes.

### Этап 7 — Проверка финального монтажа и качества

**Обязательный эталонный чек-лист:**
- Смысловой мост «стоят → связывают → оказываются в машине» нельзя сводить к «стоят → машина».
- «Я хочу в туалет», «чай и сладости», «подойди ближе», «Мне нужен ответ»: не оставлять неясный вопрос или резкий непонятный переход.
- Не обрывать крик и эмоциональный payoff перед концом исходного действия.
- «Сошлись/договорились → найти ей мужа» и «не уверен → что ты здесь делаешь»: не терять связующий контекст.
- Случайные вырезы длиной 1–2 кадра недопустимы, кроме явно подтверждённого художественного эффекта.
- Важная реакция, юмор, короткая сцена, silent physical transition сохраняются, если удаление разрушает смысл.
- Нет «сцена неизвестна» без отмеченного `uncertain` и допустимого фолбэка.
- Таймкоды и исходные PTS не выдуманы, текст ASR не перебивается, FFmpeg outputs декодируются, музыка/субтитры/звук корректны.

Проверять автоматические контракты и выборочный ручной просмотр эталонных отрывков/полученных Shorts. Оптимизация считается неприемлемой, если ускорение сопровождается существенной потерей причинно-следственных связей.

### Этап 8 — Финальный E2E, масштабирование, эксплуатация

1. Проверять каждый маленький коммит: `pytest`, API, React, Windows scripts, 180s **технический** FFmpeg E2E в GitHub. Эта группа не симулирует локальные модели и не доказывает скорость ASR/VLM.
2. Только после зелёных CI запускать 180s **полный** тест на Windows с действительной ASR/VLM. Сравнивать строго тот же исходник и модель; `TIMEOUT` остаётся FAIL; ( le 30 ) минут включая предварительные проверки.
3. Публиковать автоматически `checks.json`, `stage_timings.md/json`, `ai_diagnostics.json` в `test-reports`, без файлов с исходной речью/видео и конфиденциальными параметрами.
4. При успешном 180s PASS — отдельный 5–10-минутный тест масштабирования и затем полный ~23-минутный выпуск. Никаких обещаний линейного времени без данных.
5. Для длинного теста мониторить расход памяти, деградацию after N scenes, долю повторов, успешное возобновление после отключения/тайм-аута и качество первой/последней сцены.
6. Регрессионный мониторинг: при изменении ключевого файла сравнивать stage p50/p95 latency, request counts, долю uncertain, качество и time-to-first-render. Зелёный тест при серьёзной деградации скорости должен отмечаться отдельно как PERF-REGRESSION.
7. После каждой фазы сохранять commit SHA, список изменённых файлов, таблицу до/после, тестовые результаты, известные риски; изменение `main` только отдельным осознанным действием.

| II — главный bottleneck | 2 | Оптимизированное смысловое сокращение и доказанные удаления | `condense` полностью завершается на 180 с, качество выдержано |
| III — объём входных доказательств | 3–4 | Уменьшение количества кадров/дублирующихся проверок без потерь | сцены, речь и мосты не хуже baseline |
| IV — инфраструктура ИИ | 5–6 | Быстрая загрузка и инференс; безопасное повторное использование решений | нет деградации JSON/качества, правильная инвалидация |
| V — приёмка и масштаб | 7–8 | Полный PASS за 30 минут и проверенное масштабирование | реальные файлы MP4/SRT/audio, кэш, эталонные связки |

**Начинать реализацию с волны I, а сразу после её измерений — с этапа 2.** По текущим цифрам чрезмерное число проверок смысловых границ уже удалось сократить; максимальный риск дальнейших экспериментальных изменений — упрощение 9B-решений о вырезках, поэтому quality gate должен быть построен заранее.

### Волна II — первый узкий эксперимент: классификация титров без reasoning (2026-10-10)

В тесте `20261010_111537_551dbe1a` Qwen9B на `credit_classifier` потратила 132.283 с (556 output-токенов; 122.778 с decode), на `choose_units` — 147.159 с (593 output-токена; 131.383 с decode). Скорость 9B около 4.5 выходных токена/с, загрузка лишь 12.125 с. Следовательно, простая проверка титров с `thinking=True` потенциально расходует дорогой reasoning-бюджет.

Эксперимент: только для `credit_classifier` посылаем `chat_template_kwargs.enable_thinking=false` и не прибавляем 512 токенов reasoning к `max_tokens=130`; остальные `choose_units`/`verify_omissions` и safety gates остаются без изменений. Значение `LocalVision.thinking` самой сессии не меняем. Сторонние провайдеры не затронуты; версия кэша `STORY_VERSION` повышена для инвалидации старого решения. Не заявляем ускорение, пока локальный тест с настоящим 9B не покажет выходные токены, качество и время.

**Приёмка:** 9B `credit_classifier` возвращает те же валидные bool/confidence, смешанные титры+сюжет не превращаются в `credit_montage`, запросы на сюжетные вырезки по-прежнему reasoning-enabled, FFmpeg E2E и регрессии зелёные. По результату — идти к A/B длины/think-budget `choose_units`, а не принудительно сокращать обоснования удалений.


### 10 октября — расширение проверки и общий расход токенов

### Эксперимент: Qwen4B локально + ограниченный DeepSeek Flash для сюжета

Последний тест: 2 запроса `story9b/choose_units` — 4182 входных, 1216 выходных токенов за 326.8 с. Официальный тариф Flash: от $0.15/$0.60 за миллион входных/выходных токенов вне пика, в пике $0.30/$1.20. $0.13 может покрыть десятки аналогичных текстовых обращений, но цена визуальных входов и повторы могут отличаться. Не гарантия суммы.

Режим `local_flash_story` включается только при осознанном выборе. Whisper и Qwen4B выполняют ранний анализ локально. На story-стадии Flash получает промпт и, когда необходимо, страницы исходных кадров. До **8 сетевых HTTP-попыток на серию**, включая неудачные: резервация записывается до отправки, неизвестные по исходу вызовы не повторяются. После лимита/ошибки — локальная 9B без подмены результата. Ограничение по числу запросов, а не точный долларовый лимит. Финальные pacing/framing остаются локальными ради контроля качества.
