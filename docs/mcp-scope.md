# Предлагаемый состав MCP для КАДР

Статус: реализован первый выпуск двух stdio-подключений, 2026-10-13. [Инструкция и фактические ограничения](mcp.md). Основа — app/server.py, app/finishing.py и файлы диагностики. Работа продолжается в codex/dramatic-montage; продуктовый main не изменяется.

Два отдельных набора инструментов и точки подключения: продуктовый `kadr_*` и разработческий `kadr_dev_*`. Разработческий набор подключается отдельно и не импортируется продуктовым запуском. Они используют существующие сервисы/API КАДР; не копируют алгоритмы анализа, планирования или экспорта. Studio остаётся единственным графическим интерфейсом.

Таблицы ниже сохраняют исходный состав и основания возможностей. MCP-описания, входные схемы и адаптеры реализованы; дополнительные get_operation и cancel_check обеспечивают просмотр replay journal и отмену изолированных проверок. Для динамических callers, несохранённых model bodies, неизвестных ресурсных метрик и cache compatibility ответ содержит явные ограничения.

## 1. Управление продуктом

| Возможность | Предлагаемые инструменты | Что получает пользователь/ассистент | Основа и что добавить |
|---|---|---|---|
| Состояние приложения | `kadr_get_app_status` | Готовность, версия backend/UI, занятость | health/identity API есть; собрать согласованную сводку |
| Поиск проектов и серий | `kadr_list_projects`, `kadr_list_episodes`, `kadr_get_episode` | ID, названия, номер серии, источник, настройки и задания | library API есть; добавить фильтры и ограничение размера ответа |
| Создание проекта и серии | `kadr_create_project`, `kadr_create_episode` | Реальные записи каталога | API есть; не создавать повторно при повторе одного запроса |
| Источники | `kadr_list_sources`, `kadr_import_video` | Зарегистрированные источники; результат проверенного импорта выбранного файла | sources/import API есть; определить контракт передачи выбранного файла, без произвольного обхода дисков |
| Настройки анализа | `kadr_get_settings`, `kadr_update_settings` | Провайдер, оформление, редакторские настройки в пределах разрешённых backend-полей | часть API есть; единая публичная схема и согласованные ограничения изменения занятой серии |
| Управление обработкой | `kadr_start_job`, `kadr_resume_job`, `kadr_cancel_job` | ID реально запущенного/продолженного задания и результат отмены | create/retry/cancel API есть; проверять принадлежность задания серии и защитить запуск от дублей |
| Прогресс и ошибка | `kadr_get_job_status`, `kadr_wait_job_update` | Каждая галочка: статус, процент, сколько из скольки; конкретная ошибка | job API есть; добавить ожидание изменения по revision без частого опроса |
| Результат монтажа | `kadr_get_plan`, `kadr_get_outputs`, `kadr_get_quality_summary` | Части, длительности, субтитры, замечания, ссылки на готовые файлы | plan/files API есть; выдавать сводку и страницы вместо огромного JSON |
| Оформление | `kadr_get_finishing`, `kadr_update_finishing`, `kadr_get_captions`, `kadr_update_captions` | Профиль серии, оформление, музыка, правки подписей | finishing/captions/music API есть; сохранять проверку revision и разрешённые значения |
| Предпросмотр и экспорт | `kadr_create_preview`, `kadr_get_preview`, `kadr_start_export`, `kadr_get_export`, `kadr_save_outputs` | Асинхронные задачи, их статус и проверенные MP4/SRT | API есть; возвращать task ID сразу, согласовать явную папку назначения |
| Ручные пакеты Antigravity | `kadr_list_analysis_packets`, `kadr_prepare_analysis`, `kadr_import_analysis_result` | Состояние пакетов, проверенный импорт результата и следующий шаг | API есть; сохранить текущий контракт отдельно запускаемого пользовательского сценария |
| Архив проектов/серий | `kadr_archive_project`, `kadr_archive_episode`, `kadr_restore_project`, `kadr_restore_episode` | Обратимое архивирование и восстановление | API есть; проверить точный ID и наличие связанных активных задач |

Физическое удаление пользовательских файлов/заданий и массовая очистка не входят в первую версию MCP. Такие операции требуют отдельного спроектированного контракта. Исторические balance/recovery/spending endpoints не становятся MCP-командами.

## 2. Инструменты разработки

| Возможность | Предлагаемые инструменты | Что можно найти | Основа и что добавить |
|---|---|---|---|
| Карта проекта | `kadr_dev_get_architecture`, `kadr_dev_find_owner` | Где реализована возможность, какой модуль отвечает и какие зависимости допустимы | app/README.md и docs/audit уже есть; связать с актуальными файлами |
| Поиск в коде | `kadr_dev_search_code`, `kadr_dev_find_symbol`, `kadr_dev_get_callers` | Определение, импорты, вызовы, места регистрации маршрутов | добавить поиск по разрешённым каталогам и AST-индекс с отметкой полноты для динамических вызовов |
| Документация и решения | `kadr_dev_search_docs`, `kadr_dev_get_decision` | ADR, ограничения, схемы, известные проблемы и команды проверки | документация есть; поиск с путём и строками, отдельно исторические и текущие описания |
| Журналы выполнения | `kadr_dev_get_log_tail`, `kadr_dev_get_stage_events` | События нужного job/run/stage, последние строки, первое наблюдаемое исключение | logs и diagnostics/pipeline есть; ограниченный reader, фильтры, курсор и скрытие секретов |
| Диагностика Studio | `kadr_dev_get_ui_diagnostics` | Ошибки браузера, неуспешные действия, версия ресурсов, расхождения отображения с API | client diagnostics/identity есть; связать записи с заданием и различать отсутствующие данные и отсутствие ошибки |
| Разбор сбоя | `kadr_dev_get_error_report` | Тип/код ошибки, сообщение, traceback при наличии, пакет/сцена, контекст и ссылки на исходные события | ошибки распределены по job, worker.log и timeline; нужен связанный отчёт, без выдуманной причины |
| Проверка checkpoints | `kadr_dev_inspect_checkpoint`, `kadr_dev_compare_identities` | Какие этапы завершены, подходит ли кэш, какие подписи расходятся | checkpoints/semantic_identity есть; read-only объяснение, без изменения signatures или автоматического удаления |
| Запросы к моделям | `kadr_dev_list_model_requests`, `kadr_dev_get_model_request` | Назначение запроса, вход/ответ, schema validation, повтор, пакет, токены и время при наличии | журналы и пакеты есть; единый индекс, постраничное чтение, закрытые настройки исключить |
| Скорость и нагрузка | `kadr_dev_get_metrics`, `kadr_dev_compare_runs` | Время этапов, ожидание/генерация, число запросов, размер пакетов, cache hits, измеренная нагрузка и токены | model_perf/token_usage/timings и отчёты есть; нормализовать измерения, неизвестное оставить null |
| Прослеживание материала | `kadr_dev_trace_source_unit`, `kadr_dev_get_evidence` | Источник → ASR/кадры → сцена/единица → решение/доказательство → сюжетная связь → cut → часть результата | pipeline audit/plan есть; построить связи по настоящим ID и source-time ranges |
| Проверка плана | `kadr_dev_validate_artifact`, `kadr_dev_explain_selection` | Ошибки схемы, потери речи, связи, концовки, причины сохранения/удаления и unresolved | validators/planner_audit/quality есть; вызывать без inference и восстановления, возвращать нарушения |
| Изолированные проверки | `kadr_dev_list_checks`, `kadr_dev_run_check`, `kadr_dev_get_check_result` | Какие проверки существуют, воспроизведение сбоя, фактический stdout/exit code | verify_project/pytest/Studio checks есть; whitelist команд, изоляция, бюджет и отмена |
| Тестовые прогоны | `kadr_dev_prepare_benchmark`, `kadr_dev_start_benchmark`, `kadr_dev_get_benchmark` | Сравнение алгоритмов/провайдеров на заданном коротком отрезке | benchmark scripts есть; отдельное тестовое задание, входной диапазон и ресурсные ограничения, без подмены продуктового job |
| Состояние разработки | `kadr_dev_get_workspace_status`, `kadr_dev_get_diff` | Ветка/SHA, изменённые файлы, разница с main и связь с версией работающего backend | Git и studio_identity есть; read-only запросы и скрытие чувствительных файлов |

Редактирование файлов и Git merge/push остаются в обычном рабочем процессе разработки. MCP для поиска и диагностики не получает универсального исполнения shell, произвольного удаления или возможности обходить quality gate. Отчёт о сбое различает подтверждённую причину, наблюдаемый симптом и гипотезу.

## Общие контракты, необходимые обоим наборам

1. Явные project_id/episode_id/job_id. На запуске и изменении сервер сверяет связь и возвращает название проекта/номер серии. «Текущий экран» не определяет цель скрытым образом.
2. JSON Schema входов и структурированных результатов, версия контрактов, единые коды ошибок и проверка backend identity/совместимости.
3. Долгие операции возвращают task ID сразу. Ожидание MCP ограничивает только длительность ожидания ответа клиентом: продуктовый монтаж от этого не отменяется и не получает тестового лимита.
4. Изменяющие команды защищены от повторного запуска одним и тем же operation ID. Изменения настроек используют revision, чтобы не затереть правки Studio.
5. Отдельные возможности чтения и изменения; изменения и обращения к источникам отражаются в журнале. Разработческий набор подключается только явно и не обнаруживается в продуктовом tools/list.
6. Пагинация, фильтры и ограничение ответа для каталогов/логов/артефактов. Доступ к реальным файлам по разрешённым ID и проверенным путям; секреты и credentials исключены.
7. Состояние и диагностика не запускают модели. MCP и Studio используют одного владельца worker/экспорта, общий кэш и те же validators.
8. Общие readers для диагностических данных не создают папки, run.json или новые стадии. Не использовать изменяющий Diagnostics.__init__ для просмотра состояния.
9. Проверки: правильная серия/задание, повтор команды, busy/cancel/resume, повреждённый JSON, недоступный backend, скрытие секретов, отсутствие запуска модели при чтении, изоляция dev-команд.
10. Локальное подключение и отдельные разрешения product/dev. Транспорт и способ включения определяются при реализации; служебные установки, процессы, кэши и generated-файлы остаются внутри проекта. Разделение tools/list дополняется серверной проверкой разрешений, а не заменяет её.

MCP resources можно использовать для чтения архитектуры, схем и отчётов с устойчивыми адресами. Вызовы действий оформляются tools. В обоих случаях сохраняются ограничения доступа и объёма данных.

## Порядок реализации

1. Каркас протокола, контракты и доступ только к продуктовым операциям чтения: app status, библиотека, job status, plan/outputs/quality.
2. Отдельный dev-набор: поиск кода/документов, logs, error report, checkpoint/metrics и trace source unit. Это даст основную пользу при поиске нынешних ошибок и задержек.
3. Продуктовое управление: start/resume/cancel, settings, finishing, preview/export; затем ручные пакеты и архив.
4. Dev-запуск проверок/benchmarks после изоляции и измерения их побочных эффектов.

Первый выпуск продуктового набора должен управлять реальными данными через существующие сервисы. Разработческий набор расширяется по фактическим задачам; отсутствие данных или неполнота индекса обозначаются явно.

Официальные определения [tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) и [resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources).
