# Anime projects and episode subprojects

The user requires separate project selection, episode selection, editing and review. A single screen with global sources/jobs mixed ownership and made one episode's results hard to distinguish.

Use additive `data/library.json` version 1: anime projects have UUID identities/titles; episode records have a project UUID, unique episode number, one registered source UUID, saved editing/provider settings. Existing UUID job directories remain processing attempts. New jobs persist `episode_id` before worker startup. Legacy job associations live in the catalog; migrations group the same registered source into one episode and infer title/number from filenames. No exports, checkpoints or billing records are moved or erased. Migration is idempotent.

The existing server/manager own the catalog under the manager mutex and server instance lock. Atomic writes preserve persisted state; a failed write reloads it. Episode-bound APIs validate enums, IDs, source ownership, duplicate episode numbers and readiness; source replacement across episodes is rejected. Settings saves do not invoke paid analysis. Active episode processing rejects settings changes, including migrated legacy attempts. Legacy job APIs retain behavior.

`library.js` owns four hash routes: projects, anime episode list, episode editing, episode review. `app.js` retains import, accounting, worker controls, timeline and playback. Settings/video selection are scoped to an episode; review's montage selector contains only that episode's completed jobs. Source playback is paused when leaving review. Completing an active edit opens review; completion while browsing the library updates cards without stealing navigation. Late route/source responses cannot overwrite another episode's controls. Direct links and browser Back are supported.

Deletion uses persisted `archived_at` tombstones and a fifth `#trash` route. DELETE project/episode endpoints remove entries from active views without deleting sources, exports, attempts or accounting. An archived parent implicitly hides its children; restoring it retains any independently archived children. POST restore endpoints check active project title, episode number and source ownership conflicts before changing state. New/migrated active attempts block deletion of their episode or parent. Archived episodes release source ownership; conflicting reuse prevents later restoration. Migration keeps existing archived associations and does not resurrect deleted records. The UI exposes deletion on cards/detail screens and recovery in the main menu.

Rollback: retain a copy of library.json, revert the screen/catalog integration, and use existing job endpoints. Job directories, source registry, output files and billing remain independently usable. Removing only the catalog loses new organizational metadata, not media or exports. Migration title guesses are filename-derived, not claims about episode content.
