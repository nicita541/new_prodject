# Отчёты проверок KADR Studio

Актуальная рабочая ветка: `codex/dramatic-montage`. Запускайте проверки из папки
`F:\new_prodject\ТЕСТЫ` двойным щелчком, после обновления локальной ветки.

## Проверка без ИИ

`1_ПРОВЕРКА_БЕЗ_ИИ.bat` запускает все Python-тесты, тесты React,
сборку, lint, FFmpeg/FFprobe и 180-секундную медиа-проверку:
реальное кодирование MP4, субтитры, музыку, повторное использование кэша,
повреждение и восстановление SRT, finishing и API Range.
Это технический E2E на **синтетическом видео** и с **фиктивными смысловыми
решениями**: настоящий Whisper/ASR, VLM и DeepSeek не запускаются.

## Полная проверка с локальными моделями

`2_ПОЛНАЯ_ПРОВЕРКА_С_ИИ.bat` сначала делает техническую проверку,
затем открывает диалог выбора настоящего сюжетного видео с аудио.
Из длинной серии извлекает отдельный 180-секундный участок;
исходник не меняется. Далее запускает реальный локальный ASR и VLM,
планирование, рендеринг и проверку восстановления из кэша.

Для выбора другого участка видео (например, после опенинга):

```powershell
& ".\ТЕСТЫ\2_ПОЛНАЯ_ПРОВЕРКА_С_ИИ.bat" -RealSource "F:\new_prodject\data\imports\episode.mp4" -StartSeconds 300
```

**Для полной проверки недопустима передача готового транскрипта
(`-RealTranscript`): ASR обязан реально отработать.**
Если модель не запускается, нет исходного видео или качество не проходит
проверку, отчёт будет FAIL, а не ложный PASS. Первый прогон локальной
модели может длиться значительно дольше технического.

## Где результаты

Локально, по идентификатору запуска:
- `temp\verification-reports\<run_id>\checks.json` и `summary.md`
- `logs\tests\<run_id>\` — полные диагностические логи

После любой из двух проверок очищенная сводка автоматически публикуется
в GitHub, **в отдельную ветку `test-reports`**, по пути
`runs/<run_id>/`. Работа с отчётами не меняет текущую ветку кода,
не публикует видео, транскрипты или полные логи моделей.
Для проверки ошибок модели в GitHub публикуются только итог и
безопасная структурированная сводка этапов; подробные логи остаются на ПК.
Логи технических тестов публикуются в сокращённом виде после очистки,
но перед запуском с чувствительными данными учитывайте, что эвристическая
очистка текстов не гарантирует удаление всех приватных строк.

Нужны Git с настроенной авторизацией на запись, Python-зависимости,
`frontend/node_modules`, установленный portable FFmpeg. Если зависимости
нет, статус будет SKIP/INCOMPLETE вместо PASS. Ошибка отправки отчёта
не стирает локальный результат и приводит к отдельному коду выхода,
если сам тест завершился без ошибок.

## Отладка без загрузки и без тяжёлой обработки

Из PowerShell можно вызвать скрипт напрямую:

```powershell
.\scripts\verify_project.ps1 -Quick -NoUpload
```

`-Quick` запускает сокращённые тесты без 180-секундного рендера,
`-NoUpload` отключает отправку. В отличие от `-Quick`, обычный BAT
«без ИИ» запускает **полный технический конвейер**.

Скрипты находятся в `scripts/verify_project.ps1`,
`scripts/full_pipeline_3min.py`, `scripts/prepare_real_test_video.py`.


## Ограничение времени и ускоренная проверка сцен

Для полного теста с локальным ИИ установлен общий тайм-аут **30 минут
(1800 секунд)**, включая технические проверки, распознавание, визуальный
анализ, монтаж и проверку кэша. Это предельное время, а не гарантия PASS.
Если лимит закончится, скрипт пометит этап TIMEOUT, сохранит диагностические
логи локально и отправит очищенный отчёт в `test-reports`. Следующие проверки
после исчерпания лимита не запускаются.

Детектор теперь сохраняет все исходные кандидаты смены плана, но выбирает
не более одного наиболее информативного неоднозначного кандидата за каждые
1,5 секунды для дорогостоящей проверки границы в VLM. Остальные кандидаты
остаются видимыми в исходных планах и получают отметку неопределённости —
они не становятся ложноподтверждёнными смысловыми сценами.
Технические визуальные фрагменты ограничены 18 кадрами вместо 12;
исходные временные интервалы и кадры не отбрасываются.

Это оптимизация количества запросов, а не изменение длительности видео.
Сравнивайте количество `semantic_scenes`, `analysis_chunks`, VLM-запросов
и качество полученных сюжетных связей с предыдущим остановленным прогоном.


## Проверка реального результата против ложного PASS

Каждый запуск `full_pipeline_3min` или `real_model_3min` дополнительно
проверяется по `report.json` **в текущем каталоге прогона**, а не только
по коду выхода Python. Обязательны `status=passed` и хотя бы один
успешный шаг без ошибок. Для реального ИИ дополнительно требуются
подтверждённые запросы локальной модели, режим ASR+VLM, успешный
повторный запуск с повторным использованием кэша и неизменные файлы
рендера. Отсутствующий, повреждённый или отрицательный отчёт — FAIL.
Подробные ошибки и исходные диалоги остаются только в локальных логах.


## Автоматические структурированные логи ИИ

После полного теста с локальными моделями, даже при FAIL или TIMEOUT, автоматически создаётся и отправляется файл **ai_diagnostics.json** вместе с checks.json в test-reports/runs/<run_id>. Внутри — этап, тип ошибки, длительности, количество сцен, статистика запросов к VLM, последние события и числовой прогресс. Команды PowerShell для копирования логов больше не требуются. Публикуются только явно разрешённые числовые показатели и служебные имена; **не** публикуются видео, кадры, речь, промпты, ответы ИИ, текст исключений, абсолютные пути или сырые файлы модели. Полные локальные логи остаются на ПК.


Для отправки диагностики уже завершённого теста без повторной обработки можно один раз запустить файл **ТЕСТЫ/3_ОТПРАВИТЬ_ПОСЛЕДНИЕ_ЛОГИ_ИИ.bat**. Он загружает только ai_diagnostics.json в соответствующий существующий каталог test-reports. Рабочая ветка проекта не меняется.


## Время каждого этапа — автоматический отчёт

Каждый запуск записывает **stage_timings.md** (читаемая таблица GitHub) и **stage_timings.json** (для автоматического анализа) в `test-reports/runs/<run_id>/`. Они содержат:

- Суммарное время проверки до подготовки отчёта (публикация Git отдельно), а также каждый последовательный этап: Python, React, FFmpeg, подготовка 180 секунд, технический E2E и полный прогон ASR/VLM.
- Вложенные этапы технического E2E и реального монтажа (распознавание речи, поиск видеопланов, смысловые границы, анализ, сжатие сюжета, рендеринг и проверки кэша) с измеренным временем.
- Число и суммарную длительность запросов к моделям, самые медленные этапы, долю времени от полного прогона.

Вложенные стадии перекрываются: `pipeline` включает `scenes`, а `scenes` может включать `semantic_boundary`; **их длительности нельзя складывать**. Для старых тестов без счётчиков всего прогона выводится *not measured*, а не выдуманное число. Тесты с `FAIL` и `TIMEOUT` тоже публикуют уже измеренные стадии. После окончания старого запуска третья кнопка `ТЕСТЫ/3_ОТПРАВИТЬ_ПОСЛЕДНИЕ_ЛОГИ_ИИ.bat` досылает оба отчёта без повторного запуска модели.


## План ускорения по измерениям 2026-10-10

Исходный прогон 180 с: `scene_detection` 506,8 с (из них `semantic_boundary` 424,5 с), `analyze` 890,4 с (из них `scene_analysis` 677,8 с), после чего `condense` не успел до 30-минутного лимита. Зафиксированы 18 смысловых сцен, 70 сохранённых технических фрагментов, 181 запрос к VLM на момент TIMEOUT. Эти длительности вложены и не складываются с родительскими.

1. **Этап A — экономный отбор границ.** Для обычных слабых гипотез смены ракурса интервал проверки VLM увеличен до 3 с; для диалоговых разрывов, физического состояния, затемнений и доказанных сильных визуальных изменений сохранён 1,5 с. Непроверенная граница остаётся `triage_deferred` — не превращается в подтверждённую сцену.
2. **Этап B — контекст изображений только на входе/выходе сцены.** Для внутренних технических фрагментов убраны изображения далёких соседних смысловых сцен; собственные кадры CURRENT и текстовая информация о соседних сценах сохранены. Изменён компонентный ключ кэша во избежание использования старой несовместимой раскладки изображений.
3. **Этап C — метрики и регрессии.** В `ai_diagnostics.json` добавлены числа проверенных/отложенных границ и количество контекстных страниц. Тесты проверяют немые переходы, физические действия, короткие планы, отсутствие потерь исходного покрытия и кэширование.
4. **Этап D — реальное сравнение.** После CI запускать прежнюю 180-секундную серию с 30-минутным бюджетом, сравнить время семантических границ, первичного анализа, частоту восстановления, число сцен и завершённость рендера. Цель — реальный PASS за 30 минут без ухудшения смысловых мостов, а не искусственный PASS через отключение проверок.
